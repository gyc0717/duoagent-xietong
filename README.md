# 多 agent 协同 · 全自动工作流

> 六个异构智能体，一条 9 节点的链路，三级审核串行卡质量门禁。
> 不是把六个模型拉个群聊天——是按「层级」分工：谁派单、谁干活、谁验收、谁收口，全是定死的。

一句话：**WorkBuddy 管分发与交付，Harness 编程兼一审，Kimi 生图，豆包交谈兼三审总结，
Marvis 管电脑里的大文件，千问做外部检索与异构复核**；工件统一走 L3 中转站交换，
主链 9 个节点、入口并行 2/2、执行并行 3/3，三级审核链 N5 → N6 → N7 不可换序。

---

## 为什么不能"平级拉群"

四个模型平级扔进一个群，会同时出现三个问题：

1. **派单歧义**——一个任务给谁？谁能改谁？没有层级就没有仲裁。
2. **审核同源**——让同一个模型自查，等于自己给自己判卷。
3. **上下文打架**——每个模型的上下文窗口和工具集不一样，硬塞一份任务描述必然截断。

所以这套方案从第一版就定了：**五层架构 + L3 协同中间层 + 9 节点 DAG**，
角色按职责分完不留空位，能力缺口用「挂在调用点上」的方式补，不新增平级角色。

## 六方分工

| 成员 | 职位 | 职责 | 链路位置 |
|---|---|---|---|
| DeepSeek Harness | 首席开发 / 主程，兼一审 | 全部编程实现；深度 4 轮校验 | 执行主体 + 审核第一关 |
| Kimi | 视觉设计师 | 图表、信息图、可编辑 PPT 视觉层 | 执行阶段并行 |
| 豆包 | 对外沟通官 | 交谈、澄清、三审、面向人的总结 | 审核链最后一关 |
| WorkBuddy | 项目总监 | 拆解分发、二审、聊天界面收口 | 头尾都管 |
| Marvis 马维斯 | 本地资料管理员 | 大文件索引、切片、按需全文加载 | 执行阶段并行，私有不出本地 |
| 通义千问 | 外部调研 + 独立复核 | 联网检索、异构交叉复核、L0 备选模型 | 三个窄职责，不占平级编制 |

千问为什么不做第六方：它是通用大模型，平级加入会造成"派给谁"的歧义，
还会在定死的三级审核链上多一个输出源。所以只挂三个调用点（N1Q 检索 / N5 内复核 / L0 路由）。

## 链路

```
N1  WorkBuddy 派单  ∥  N1Q 千问检索          ← 入口并行 2/2
        ↓
N2  Harness 接入  ∥  N3 Kimi 生图  ∥  N4 Marvis 取大文件   ← 执行并行 3/3
        ↓
N5  Harness 深度一审（同源 + 沙箱实证 + 千问异构复核）
        ↓
N6  WorkBuddy 二审
        ↓
N7  豆包三审 + 总结
        ↓
N8  WorkBuddy 收口 → 聊天界面
```

**硬约束**：性能 / 质量不降级。token 与成本只记账、不设下降目标；裁剪上下文换省钱的做法一律禁止。


## 三分钟跑起来

```bash
# 1) 零密钥 PoC：生成完整工作区，9/9 节点跑完
python poc/multi_agent_poc.py

# 2) 看结论
cat cohort/outbox/final.md
cat cohort/ledger.jsonl          # 成本台账
cat cohort/run_log.jsonl         # 52 条 append-only 审计

# 3) 跑测试与验收
python run_tests.py
python acceptance.py             # 15 项逐条核验
```

真数据、真模型、L3 网关、MCP 接入的完整跑法见 **[使用说明.md](使用说明.md)**；
跑出来的图表、报告与验收证据见 **[效果展示.md](效果展示.md)**。
